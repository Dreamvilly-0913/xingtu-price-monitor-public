日期：2026 年 10 月 4 日。本文记录 [Docker 部署验收报告](Docker部署验收报告.md) 中三个 P1 问题的修复。原验收的 **499 项断言、496 项通过、3 项失败**保留为修复前证据，不改写历史结果。

本文记录修复设计、实际回归、Docker故障注入和正式升级；原失败记录单独保留，不覆盖为通过。

## 1. 冷却重入时漏计当前预警

原场景为目标价 90 元，价格 80 → 95 → 80 元。第一轮触发、第二轮解除后，第三轮在 24 小时冷却期内不生成重复提醒，同时也错误地显示没有当前预警。

新增 `AlertRuleState` 保存当前规则评估状态，提醒流水 `Alert` 保存触发时的价格、时间、已读状态与原提醒解除时间。采集后同一事务更新当前规则状态；冷却及未处理去重只约束是否生成新提醒。

- 再次达标时当前规则恢复为触发中，提醒流水仍遵守 24 小时冷却。
- 仪表盘、预警中心、商品详情从当前规则状态读取活动数量；页面同时显示当前规则与历史提醒。
- 标记已读改变提醒的已读状态，不解除仍满足条件的规则。
- 规则状态关联实际成功采集点与采集口径，停用、过期、配置失配及演示关闭仍会解除失效状态。
- 启动旧库时依据已有采集流水恢复规则状态，不补造价格或历史提醒。

主要代码：`server/src/alerts.ts`、`dashboard.ts`、`routes.ts`、`serializers.ts`、`client/src/pages/AlertsPage.tsx`。

## 2. Docker 默认停止窗口不足

原 18 秒 HTTP 采集在默认 Docker 停止窗口内未能完成，被强杀，退出码 137。

Compose 设置 `stop_grace_period: 45s`，为已有采集器的最长 30 秒 HTTP 超时及落库预留时间。`preClose` 立即阻止新采集、未开始队列和 cron 派发，启动停止任务后马上返回；`onClose` 等待同一停止任务完成落库。

第一版把等待放进 `preClose`，真实 Docker 复验仍失败：单件和六件队列分别在 45,878ms / 45,874ms 被强杀（137），尽管采集约18秒已结束。原因有两项：Fastify/Avvio 的 `preClose` 共享默认10秒插件预算；在途请求返回后，keep-alive连接还会阻塞关闭，默认可达72秒。该首轮的6项失败及日志保留在本次证据目录，没有更改验收窗口。

第二版把等待移到没有插件加载超时的 `onClose`，并为停止期间的在途响应设置 `Connection: close`，完整返回后自然关闭连接；不提前销毁在途请求。信号处理共用一个关闭任务，记录开始停止、HTTP/采集排空和数据库连接关闭三个阶段。

原先只有 `onClose`，整轮采集的 HTTP handler 尚未结束时无法及时停止派发。现在站点队列在轮到执行前复查停止状态，等待中的站点冷却定时器也可以取消。未派发任务明确记为中断，不生成虚构采集价格或失败流水。

全量回归还发现，新任务账本的前置数据库写入会造成同站点实际请求间隔缩短。修复后从上一项完整任务结束开始冷却，使用单调时钟并复查等待截止时间；跨站点并发仍保持，同站点实际启动间隔至少达到配置值。原间隔断言没有放宽。

主要代码：`compose.yaml`、`server/src/app.ts`、`index.ts`、`collection-service.ts`、`scheduler.ts`。

## 3. 强杀后的中断轮次不恢复

新增持久化任务账本 `CollectionRunItem`，每轮按启用商品创建任务，状态为 `pending`、`running`、`success`、`failure` 或 `interrupted`。采集流水增加可空 `runId`，任务关联实际采集流水。

采集流水、任务完成状态和轮次成功/失败计数在同一事务提交；事务任何一步失败，三者一起回滚。提交后 DTO 组装失败或重复收尾不会将已保存成功任务改成失败，也不会增加重复计数或再造价格点。

启动时在启用 cron 前结束遗留 `running` 轮次：从任务账本恢复已完成计数，未完成项目记为中断，并保存结束时间和原因。恢复不重新写入已有价格。中断商品可手动或下一轮重新采集。

新版本轮次结束后满足：

```text
total = successCount + failureCount + interruptedCount
```

手动单商品采集无需强制创建全局轮次。任务的商品 ID 不设置商品外键，避免商品在采集期间被删除后丢失轮次派发与结束证据。

### 老版本无任务账本的限制

旧流水没有可靠的轮次关联，不能仅凭时间窗口猜测它属于哪一轮。此类遗留轮次标记为中断并保存结束时间，保留原有已知成功、失败及中断计数；错误说明明确写出“未完成数量无法可靠还原”。不强行把 `total` 的差额填成失败或中断，更不补造价格。

因此上述计数守恒适用于拥有完整任务账本的新轮次，旧轮次的未知数量继续如实保留。

主要代码：`server/prisma/schema.prisma`、`server/src/run-progress.ts`、`collection-service.ts`、`scheduler.ts`。

## 6. 环境故障与恢复记录
